# Контракт объекта splify2 в rpcd

splify2 отдаёт веб-интерфейсу (и любому авторизованному вызывающему rpcd) объект `ubus`/`rpcd` с
именем **`splify2`**. Этот документ — контракт того объекта: методы, их вход и выход.

splify2 — тонкая обёртка на shell поверх движка [steer](https://github.com/xyzmean/steer). Методы,
спрашивающие состояние или диагностику (`status`, `diag`, `vless_nodes`, `explain`), зовут
соответствующую подкоманду движка и возвращают её JSON **дословно**. Это сделано намеренно: разбор
вывода движка здесь означал бы вторую модель данных на shell, которая расходится с движком при первом
же его изменении. Печатает движок JSON — обёртка пропускает его без правок; не печатает — обёртка
отвечает единым объектом ошибки.

## Соглашения

- **Транспорт.** Каждый метод, принимающий вход, читает его как **JSON на stdin**, а не позиционным
  аргументом. (`steer_install` раньше читал свой блок из `$2`; его привели к общему виду, и теперь он
  тоже читает stdin. Вызывающий, передающий блок позиционно, получит пустые значения и ошибку.)
- **Успех** — форма, описанная у каждого метода.
- **Ошибка** — единый объект у всех методов:

  ```json
  { "ok": false, "error": "причина по-русски, для человека" }
  ```

  Методы, проксирующие движок, отвечают этим же объектом, когда движок не выдал годного JSON —
  например, `{"ok":false,"error":"движок не ответил"}`.

  **Ненулевой код возврата движка сам по себе ошибкой не является:** `diag` и `vless-probe`
  завершаются с `1`, когда нашли проблему, но JSON при этом валидный, и он возвращается как успех.
  Полная таблица кодов — в контракте steer, §6.

- **Важно для вызывающего: отказ приезжает УСПЕШНЫМ вызовом.** Объект ошибки отдаётся с **нулевым**
  кодом возврата скрипта, поэтому промис в браузере резолвится, а не отклоняется. Проверять надо
  поле `ok`, а не только факт отказа вызова. Интерфейс однажды именно на этом и обжёгся: движок не
  отвечал, `status` возвращал объект ошибки, а страница красила роутер зелёным и писала «Работает».
- **Права.** Методы разделены на группы read и write в
  `luci/root/usr/share/rpcd/acl.d/luci-app-splify2.json`. Проверка на этапе сборки в `build.sh`
  роняет сборку, если объявленный метод отсутствует в ACL. Новый метод обязан появиться и в блоке
  `list)` скрипта rpcd, и в файле ACL.
- **Менеджер пакетов.** Методы установки работают и с `apk` (OpenWrt 24.10+), и с `opkg` (23.05,
  22.03): менеджер определяется на старте скрипта, и от него зависят расширение файла пакета (`apk`
  или `ipk`) и суффикс для пакета без бинарного кода (`noarch` или `all`).

## Установка движка и версии

### `steer_versions` (read)

Версии движка, доступные к установке. Спрашиваются у GitHub живьём, а не берутся из зашитого
списка: зашитый список молча ставил бы устаревший движок.

- **Вход:** нет.
- **Выход:**

  ```json
  { "arch": "aarch64_cortex-a53", "versions": ["0.9.13", "0.9.12", "..."] }
  ```

  `versions` — теги последних релизов `xyzmean/steer` без ведущего `v`, **отфильтрованные по форме
  `X.Y.Z`**. Фильтр — смысл функции, а не украшение: установка принимает только такую форму, и
  показывать в списке то, что она отвергнет, значит обещать невозможное. Поэтому вернуться может
  меньше десяти значений, и это не сбой. Разбор через `grep -o` (один тег на совпадение), чтобы
  переживать минифицированный однострочный JSON: прежний жадный `sed` схлопывал всё в один захват и
  отдавал негодный список.

### `steer_install` (write)

Скачивает и ставит указанную версию и вариант движка. Ставит **ровно запрошенный** пакет и не
угадывает вариант: выбор между базовым и расширенным зависит от того, хочет ли человек, чтобы движок
сам поднимал туннель VLESS.

- **Вход** (JSON на stdin):

  ```json
  { "version": "0.9.13", "extended": false }
  ```

  - `version` — обязательно, форма `X.Y.Z` (только цифры и точки). Иное отвергается с
    `"версия не в виде X.Y.Z"`.
  - `extended` — `1` или `true` выбирают `steer-extended`, иное — базовый `steer`.

- **Выход (успех):**

  ```json
  { "ok": true, "installed": "steer-extended-0.9.13-1_aarch64_cortex-a53.apk",
    "restarted": true, "removed": false }
  ```

  - `installed` — имя поставленного файла.
  - `restarted` — **перезапустилась ли служба движка.** Отдельно от `ok`, потому что «пакет встал» и
    «роутер маршрутизирует» — разные вещи. Внимание: `false` означает не только неудачу, но и
    «перезапускать было нечего» — на свежем роутере, где спеки ещё нет, служба не перезапускается
    намеренно.
  - `removed` — снимался ли прежний вариант пакета. Значимо: значит, движка на роутере в какой-то
    момент не было.

- **Выход (отказ):** стандартный объект ошибки с одной из причин: `"версия не в виде X.Y.Z"`,
  `"не определилась архитектура"`, `"не скачалось: <имя> (нет такой версии для <арх>?)"` либо
  перехваченный вывод менеджера пакетов.

- **Порядок установки.** Сначала **ставим**, и только если менеджер пожаловался на конфликт — снимаем
  прежний вариант и ставим снова. Порядок здесь не стиль, а разница между «установка не удалась» и
  «роутер больше не маршрутизирует»: удаление пакета запускает его `pre-deinstall`, который
  останавливает и **отключает** службу, а остановка движка сносит таблицу nft и вычищает `ip rule`.
  Пока удаление стояло первым, любой отказ установки — не та архитектура, кончилось место, битый
  файл — оставлял роутер без движка, без правил и со снятым автозапуском, то есть перезагрузка уже не
  спасала. И всё это в ответ на «обновить». Обновление в пределах одного варианта, самый частый путь,
  через удаление вообще не проходит.

  Шаблон распознавания конфликта намеренно узкий — только слово «конфликт». Общее
  «unable to select packages» сюда не годится: менеджер печатает его на любую неудовлетворимую
  зависимость, включая «нет nftables», и снимать по нему рабочий пакет значило бы вернуть ровно ту
  поломку, ради которой порядок и переставлен.

- Ставится с `--force-overwrite` (базовый и расширенный владеют одним `/usr/sbin/steer`), для `apk`
  дополнительно `--allow-untrusted`: пакеты не подписаны ключом репозитория OpenWrt, они лежат в
  GitHub Releases. У `opkg` проверки подписи локального файла нет вовсе, и такого флага он не знает.
- После установки служба движка включается в автозапуск.

### `splify2_versions` (read)

То же для самого интерфейса.

- **Вход:** нет.
- **Выход:** `{ "current": "0.8.0", "versions": ["0.8.0", "0.7.9", "..."] }` — установленная версия и
  доступные, тем же фильтром `X.Y.Z`.

### `splify2_install` (write)

Ставит указанную версию интерфейса. Нужен потому, что пакет лежит в GitHub Releases, а не в
репозитории OpenWrt: `apk upgrade` его не видит, и обновиться можно было только по ssh.

- **Вход:** `{ "version": "0.8.0" }`.
- **Выход (успех):** `{ "ok": true, "installed": "<имя файла>", "reload_needed": true, "removed": <bool> }`.
  `reload_needed` означает, что страницу надо перезагрузить: бандл сменился.
- **Выход (отказ):** стандартный объект ошибки.

## Состояние и здоровье движка

### `status` (read)

Применённое состояние движка. Пропускает вывод `steer status` **дословно**. Если движок не выдал
объекта, начинающегося с `{`, отвечает `{"ok":false,"error":"движок не ответил"}`. Состав полей —
контракт steer §2, включая `down_packets`/`down_bytes`.

Обратите внимание: `channels` в этом выводе — объединённые **группы**, а не исходные правила один к
одному, и `name` там — служебное имя набора nft. Читаемые имена исходных правил приходят в поле
`channels` каждой группы; именно их и стоит показывать человеку.

### `diag` (read)

Диагностика движка, вывод `steer diag` дословно. Движок завершается с `1`, когда нашёл вердикт
`fail`, но JSON печатает валидный — он возвращается как обычный ответ, ненулевой код **не** считается
ошибкой. Набор вердиктов (`ok`/`note`/`warn`/`fail`, `note` исключён из счётчиков) — контракт steer
§4. Если JSON не получен вовсе, отвечает объектом ошибки.

### `engine` (read)

Наличие и версия движка.

- **Вход:** нет.
- **Выход:** `{ "present": 1, "vless": 0|1, "arch": "...", "version": "...", "enabled": <bool>, "running": <bool> }`.
  - `vless` — расширенная ли сборка. Определяется по отказу `steer vless ''`, содержащему подстроку
    `steer-extended` (это часть контракта движка).
  - `enabled` — стоит ли служба в автозапуске; `running` — работает ли хотя бы один экземпляр.
    Спрашивается у procd, а не по наличию процесса: у движка их несколько (сам steer, резолвер,
    клиенты vless), и «жив ли процесс с таким именем» на это не отвечает. Эти два поля — источник
    состояния для переключателя «Остановить всё».

### `engine_state` (read)

Состояние экземпляров движка и последние строки их журнала. Появился потому, что «выход настроен» и
«туннель несёт трафик» — разные вещи, а упавший туннель VLESS раньше был виден только как
отсутствующее устройство, без причины.

- **Вход:** нет.
- **Выход:** по экземпляру — работает ли, pid, и последние строки его журнала **дословно**. Обёртка
  намеренно не разбирает текст сообщений движка: формулировки меняются вместе с движком, и разбор
  здесь ломал бы отображение при каждой правке сообщения. Классифицировать строки следует по
  префиксу `steer[warn]`/`steer[info]` — см. контракт steer §5.

### `engine_stop` (write) и `engine_start` (write)

Останавливают и запускают службу движка целиком, вместе со снятием и постановкой автозапуска.
Правила из ядра сносит сама остановка движка.

- **Вход:** нет.
- **Выход:** `{ "ok": true, "enabled": <bool>, "running": <bool> }` — состояние после операции, теми
  же полями, что у `engine`.

Известное поведение: ночное обновление списков применяет настройки и поднимает службу, поэтому
остановка не переживает суточный цикл. Автозапуск при этом остаётся снятым.

### `dev_stats` (read)

Счётчики байтов и пакетов по сетевым устройствам из `/sys/class/net/*/statistics` (кроме `lo`).
Нужны потому, что счётчик канала nft стоит на правиле метки в направлении LAN→WAN, и обратный поток
с устройства туннеля в него не попадает: на живом роутере это давало ~4,3 МБ против 223 МБ реально
скачанных. У устройств туннеля `rx` — то, что движок отдал клиентам (скачано), `tx` — то, что взял у
них.

- **Вход:** нет.
- **Выход:**

  ```json
  { "devices": { "awg0": { "rx": "...", "tx": "...", "rx_packets": "...", "tx_packets": "..." } } }
  ```

## Спека

### `spec_get` (read)

Текущая спека из `/etc/steer/spec.json`, либо `{"schema":1,"outputs":{},"channels":[]}`, если файла
нет или он пуст.

### `spec_set` (write)

Проверяет и сохраняет новую спеку.

- **Вход:** `{ "spec": "<вся спека строкой JSON>" }`.
- **Выход:** стандартный объект успеха или ошибки; в ошибке — текст отказа движка.

Спека проверяется `steer apply --dry-run` **до** записи: движок — единственный судья, он же будет её
применять, и на диске не должно оказаться спеки, которую он отвергнет при следующей загрузке.

Запись атомарна: временный файл создаётся **рядом** с целевым, а не в `/tmp`. `/tmp` — это tmpfs, а
спека лежит на overlay, и `mv` между файловыми системами в busybox — это копирование, а не
`rename()`: обрыв на полном overlay оставлял обрубок на месте рабочей спеки, а метод отвечал
«сохранено».

Метод считает два отпечатка и по их изменению помечает, что надо сделать при следующем `apply`:

| Отпечаток | Что попало | Что помечается |
|---|---|---|
| VLESS | `sub_file` и `node` каждого выхода `kind: vless` | Сменился набор выходов — `instances`; сменились только параметры — `params` |
| obfs | `server` и `listen` каждого выхода с `obfs` | То же различение |

Различение обязательно: сменился адрес сервера — хватит сигнала живому экземпляру, а появился новый
выход — экземпляра ещё нет, и сигналить некому. Такой выход выглядел бы настроенным и молча не
работал бы до перезагрузки роутера.

Отпечаток VLESS намеренно узкий (только подписка и номер узла): правка списков не должна менять
выходной адрес и рвать соединения через туннель.

### `apply` (write)

Применяет текущую спеку через `steer apply`.

- **Вход:** нет.
- **Выход:** `{ "ok": <bool>, "output": "<вывод движка целиком>" }`. Обратите внимание: здесь
  **нет** поля `error` — причина лежит в `output`, потому что движок объясняет её лучше, чем обёртка
  могла бы пересказать. В `output` попадает и вывод создания зоны firewall, и предупреждения движка
  (например, что у туннеля нет NAT), и сообщения о перезапущенных экземплярах.

Перед применением создаётся зона firewall для устройств `kind: vless`: `fw4` отвергает форвардинг на
устройство, не входящее ни в одну зону, и клиент получил бы «Operation not permitted» ещё до
туннеля. Зона создаётся здесь, а не в движке, потому что это управляющее решение и делается через
uci.

### `explain` (read)

- **Вход:** `{ "address": "1.2.3.4 | example.com" }`.
- **Выход:** `{ "text": "<вывод steer explain>" }` — текст движка дословно.

Аргумент уходит движку позиционным, поэтому значение, начинающееся с дефиса, будет разобрано как
флаг и вызовет отказ разбора аргументов, а не «это не адрес и не имя».

## Списки и подписка

### `lists` (read)

Манифест каталога списков; при первом вызове скачивает его. Пропускается дословно.

### `local_lists` (read)

Файлы списков, лежащие на роутере: путь, число строк, время изменения.

### `list_fetch` (write)

Скачать один список из манифеста.

- **Вход:** `{ "id": "<id списка>", "kind": "prefixes|domains" }`.
- **Выход:** `{ "ok": true, "count": <строк>, "path": "<путь>" }` или объект ошибки.

`kind` **обязателен** и объявлен в сигнатуре метода: `categories` и `domain_lists` — разные
пространства имён, и один id законно есть в обоих (у издателя так с `news` и `hodca`). Без вида
запрос уходит в ветку «искать где найдётся», где адресные категории проверяются первыми, и доменный
запрос скачал бы адресный файл под именем доменного.

Путь из манифеста проверяется: он обязан состоять из безопасных символов и не может выходить за
каталог списков. Поле `file` приходит из интернета, и без проверки значение вида
`../../../etc/crontabs/root` давало запись файла от root куда угодно.

### `list_put` (write)

Свой список — текстом, по ссылке или порциями из файла.

- **Вход:** `{ "name": "<имя>", "kind": "prefixes|domains", "text": "...", "url": "...", "append": <bool> }`.
  - `name` — только латиница, цифры, дефис и подчёркивание: имя становится частью пути на диске.
  - Ровно одно из `text` или `url`. Ссылка обязана начинаться с `http://` или `https://`.
  - `append` — **булево, не число.** Метод объявлен в сигнатуре как boolean, и число приезжает
    другим типом blobmsg: rpcd молча отбросит несовпавший атрибут, и каждая порция файла заместит
    предыдущую вместо дописывания.
- **Выход:** `{ "ok": true, "path": "...", "count": <строк итого>, "dropped": <отброшено строк> }`.

Содержимое проверяется и приводится к годному виду: одиночный адрес дополняется до `/32`, домены
приводятся к нижнему регистру и лишаются ведущего `*.`, у адресов проверяются диапазоны октетов и
длина префикса. Отброшенные строки **считаются и называются числом** — молчаливая потеря строк была
бы худшим из возможных поведений. Проверка стоит здесь, а не в интерфейсе: интерфейс можно обойти, а
последствие непроверенного списка молчаливое — nft отвергнет весь набор правил целиком.

Предел размера — 1 МБ, и считается он по **итоговому** файлу, а не по одной порции: overlay на
роутере мал, и список, который туда не влезет, положит не только себя.

### `list_remove` (write)

Удалить один список.

- **Вход:** `{ "id": "<id из манифеста>", "kind": "prefixes|domains" }` — для списка издателя,
  либо `{ "name": "<имя>", "kind": "..." }` — для своего. Ветка `name` — единственный способ удалить
  свой список.
- **Выход:** стандартный объект успеха или ошибки. Список, задействованный правилом, не удаляется, и
  метод говорит об этом причиной.

### `sub_info` (read)

Сведения о сохранённой подписке VLESS: источник, вид, размер.

- **Выход:** включает `kind` со значением `url` или `links`. **Поле значимо:** для вставленных
  руками ссылок `vless://` обновление подписки не значит ничего, и предлагать «Обновить» там не
  нужно — адреса, откуда обновляться, не существует.

### `sub_set` (write)

- **Вход:** `{ "url": "<адрес подписки | одна или несколько ссылок vless://>" }`.
- **Выход:** `{ "ok": true, "kind": "url|links", "path": "<файл подписки>", "bytes": <n> }` или
  объект ошибки.

Принимает **обе формы**: адрес подписки `http(s)://` и одну или несколько ссылок `vless://` через
пробел или перевод строки. Вторая форма заведена не для полноты: человек с одним сервером от
знакомого без неё не мог сделать вообще ничего.

## Состояние интерфейса

### `ui_get` (read) и `ui_set` (write)

Состояние мастера настройки, которое создал человек. Хранится непрозрачной строкой в uci
(`splify2.main.wizard`), отдельно от спеки: формат принадлежит интерфейсу и меняется вместе с ним,
обёртка его не разбирает.

- `ui_get` — вход: нет; выход: `{ "state": "<строка, возможно пустая>" }`.
- `ui_set` — вход: `{ "state": "<строка>" }`; выход: `{ "ok": true }`.

## Проверки и устройства

### `outbound_probe` (read)

- **Вход:** `{ "output": "<имя выхода>" }`.
- **Выход:** `{ "output": "...", "state": "ok|нет ответа|нет устройства", "ms": <мс или -1>, "how": "..." }`.

Для выхода `kind: vless` спрашивает движок (`steer vless-probe`), потому что ICMP через TUN не идёт;
для выхода-интерфейса пингует через устройство.

### `vless_nodes` (read)

- **Вход:** `{ "output": "<имя выхода vless>" }`.
- **Выход:** узлы, разобранные из подписки, дословно из `steer vless-nodes`. При отказе — стандартный
  объект ошибки, и вызывающий обязан его проверить: иначе отказ выглядит как пустой список узлов.

### `vless_probe` (read)

- **Вход:** `{ "output": "<имя выхода>", "node": <номер, -1 — первый рабочий> }`.
- **Выход:** JSON `steer vless-probe` дословно.

Один узел на вызов: проверка ограничена таймаутом, и «все узлы» вышли бы за время жизни вызова rpcd.

### `devices` (read)

Сетевые устройства, известные системе.

### `leases` (read)

Аренды DHCP — имена устройств по MAC. Нужны, чтобы в правиле можно было выбрать устройство по имени,
а в спеку положить MAC: адрес меняется, MAC живёт.

### `net_info` (read)

Сводка сведений о туннеле одним вызовом (вместо трёх отдельных вызовов ubus на каждый опрос — на
роутере с 64 МБ и одним ядром каждый вызов стоит запуска shell).

Внешний адрес здесь **намеренно отсутствует**: чтобы его узнать, запрос должен уйти *через* туннель,
а steer маршрутизирует по метке пакета, а не по адресу источника — привязка к адресу устройства
туннеля всё равно отправит запрос по маршруту по умолчанию и вернёт адрес провайдера. Уверенный
неверный ответ хуже отсутствующего.
